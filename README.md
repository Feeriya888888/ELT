# ClickHouse ELT Pipeline: аналитика интернет-магазина

проект по построению аналитического хранилища на ClickHouse в парадигме **ELT**:
данные сначала загружаются в хранилище «как есть», а вся трансформация выполняется SQL-ом
внутри самой СУБД — по классической слоёной архитектуре **raw → staging → marts**.

## Задача

Для интернет-магазина нужен отчётный контур, который отвечает на вопросы продукта:

- сколько пользователей заходило каждый день (DAU);
- как устроена воронка: просмотр → карточка товара → корзина → покупка;
- какой weekly retention у когорт пользователей;
- какие товары приносят выручку и какой канал привлечения работает лучше.

## Архитектура (ELT)

```
[Имитация источника: CSV-файлы]
        |  extract (scripts/extract.py)
        v
[raw.*   - сырой слой: строки без типизации, грузятся «как есть»]
        |  load (scripts/load.py -> INSERT ... FORMAT CSV)
        v
[stg.*   - staging: типизация, валидация, дедупликация SQL-ом]
        |  transform (sql/03_marts.sql)
        v
[mart.*  - витрины: DAU, воронка, retention, выручка]
```



## Слои и проектные решения

**raw** — все колонки `String` + служебная колонка `loaded_at` со временем загрузки.
Слой ничего не валидирует: задача raw-слоя — сохранить источник нетронутым, чтобы всегда
можно было перечитать данные заново, если в трансформации нашли ошибку.

**stg** — типизация и дедупликация. Тут появляются правильные типы:
`Date`, `DateTime`, `UInt64`, `Enum8` для событий и статусов заказа,
`LowCardinality` для каналов. Таблицы — `ReplacingMergeTree(loaded_at)`: повторная
загрузка одних и тех же строк безопасна, а в запросах используется `FINAL`.

**mart** — витрины. DAU и выручка считаются через `AggregatingMergeTree`
(`uniqState`/`sumState` + `uniqMerge`/`sumMerge`) — классический приём предагрегации
ClickHouse. Воронка и retention реализованы представлениями поверх stg, потому что
они дают гибкость по срезам, а объём событий позволяет.

Партиционирование витрин — по месяцам, TTL на staging-слое — 24 месяца.
